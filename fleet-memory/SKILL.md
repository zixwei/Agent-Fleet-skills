# Continue work through project files

When taking over work, check the project card and the handoff for your role against the actual delivery. Follow the decision ID to see why the last round ended as it did. Record obstacles as they arise so the next round can choose a rule to try and someone to check the result.

Read and write working records only inside the project chosen by the reader. The project card lives in root `AGENTS.md`; root `CLAUDE.md` imports it with `@AGENTS.md`. Handoffs, decisions, and other shared files live in `fleet/`. Tasks and deliveries also refer only to project files. Do not read or write any memory directory outside the project. Work from the project root. The paths below are for English projects. For Chinese projects, use the entrypoint installed with `--lang zh` and follow the project card for the existing working filenames.

## Let the fleet improve itself

1. When work stalls, someone has to interrupt the human, or the same correction comes up again, record what happened and where to find the evidence in `fleet/opportunities.md`. For an older project without the file, start with the [opportunity log template](../fleet-setup/templates/en/opportunities.md). Mark each entry **Idea**, **Decided, not started**, **In trial**, **Verified**, or **Withdrawn**, according to its actual state.
2. Review the log once a week. Count occurrences of the same problem. If the project has a `fleet/working-together.md` file, check the preferences recorded there. Choose a small trial only if the same kind of problem has occurred at least twice or the role authorized in the approval table has explicitly agreed to an earlier trial. If no real problem has surfaced, keep the current practice. Do not invent a problem for a demonstration.
3. Assign the trial a decision ID. Use that ID in the opportunity log and `fleet/decisions.md` to connect the original review finding and its source, the rule to try, its scope, who will check it, and the result. If there was no original review, say so and cite the handoff or opportunity entry that first recorded the problem. Set the success criterion up front and leave the result pending. Peers review the proposed rule, then a model from another provider checks it. After both reviews pass, the role authorized in the approval table decides whether to run the trial. Record that decision under the same ID. If it goes ahead, stay within the agreed scope and mark it **In trial**. The human can weigh in at any time and decides direction, external commitments, spending, and deletion.
4. The person or role assigned to check the trial compares the resulting delivery with the original criterion and appends the result and evidence location under the same decision ID. If no suitable task has come up or evidence is insufficient, keep the entry **In trial** and record who will check next and what evidence they will use. The role authorized in the approval table decides whether to keep or withdraw the rule based on the result and records why. If the change worked, mark it **Verified**, update the project rules and relevant skills with the reviewed rule, and identify the rule it replaces. If it did not help, restore the old practice, mark the status **Withdrawn** in the opportunity log, and record one sentence under the same decision ID explaining why the rule was withdrawn. The next member can follow the ID to see what happened.

## Verify the state and hand off

After a restart, session change, or context compaction, read root `AGENTS.md` and the latest section of `fleet/handoff.md` addressed to your role or task, check them against the actual state, then act. Follow the file map to the principles, roster, and decisions needed for this task. Check actual files, outputs, and task status: “in progress” in a handoff does not prove a task is still running, and “complete” does not prove its quality was accepted. Record observed discrepancies before choosing where to resume. Avoid repeating completed actions.

When the human asks to pick up the work (for example, “Continue where we left off”), check first, then open your reply with these three lines before going on:

```text
Where we stopped: …
Done since the last handoff: … (run ended, delivery received and review passed, stated separately)
Waiting for you: …
```

Write “none” for a line with nothing in it. Base all three lines on the files and the actual state, and take any dates and times in them from the system clock instead of estimating.

Treat a compacted summary as a clue, not as evidence. It can omit lasting rules, running tasks and file conventions. Read the project card and the matching handoff, then verify the state before continuing. Locate a handoff by role or task; do not simply take the last entry by date. If its intended recipient is unclear, show the relevant headings and explain that choosing the wrong one could repeat work. Ask the human here to reply with the one heading or role and task to resume. Check that choice against the project card and actual files before continuing from that point. Where the host supports it, enable an automatic reminder to read and verify these files after context compaction.

Keep the project card to one page: goal and rules, current work, decisions awaiting a human, and file map. Only the project manager role maintains the card; other roles propose changes through handoffs and the decision log. Update its contents only in root `AGENTS.md`. A new `CLAUDE.md` contains only the import line. When these files already exist, preserve other contents and maintain only the “AI Fleet project card” section and its import, or “AI 舰队项目卡” for Chinese projects. The card's first line states: After a restart, session change or context compaction, read the project card and the latest handoff addressed to your role or task, check them against the actual state, then act; before wrapping up or running out of context, write a handoff first. Use the selected project card template's exact wording. In an existing file, put the line first in that section's body. Keep only information needed to resume; leave history in the handoff and decision log.

Record anything the human must decide or answer under “Decisions needed” on the project card (other roles propose items through the handoff, and the project manager records them). Start each item with the date (`YYYY-MM-DD`), then name the role that is waiting, what the human needs to do, your recommendation, the reason, and who decides. Collect the items that do not block current work and bring them to the human together at a natural pause (for example, when a step is done or before wrapping up), asking for a reply to each; ask right away about anything that blocks work. While waiting for the reply, set that item aside and continue with work it does not block, so the whole line does not wait with it. During setup, follow fleet-setup and ask one question at a time. When the human replies, record the outcome in the decision log right away, then remove the item from “Decisions needed”.

Record important human decisions, newly agreed rules and newly started background tasks in the decision log or handoff as they happen. Do not leave them until closeout. For a background task, record its identifier, running-state evidence, how to recognize success and failure, and how to resume. Also put verified changes where the next person doing similar work will look first, such as the brief template, roster entry, or project card.

Write important handoffs in files the receiving role or task will read, and give their locations in the project card or the receiver's task brief. Messages provide prompt notice; if the messaging channel is blocked, record the handoff in files and continue authorized work that can proceed without it, rather than waiting for someone to restore the channel.

Optional: if the tool supports scheduled tasks, set it to wake periodically, read the project card and matching handoff first, and check the actual state. Write a handoff to files before each run ends so the next scheduled run can resume. The scheduler only wakes members, and it does not fire while the tool is closed or the computer is asleep. Re-queuing work after a milestone, routing items that wait for a human and telling a person about failures depend on members following this section; this package does not enforce them. On waking, take up the next queued item before checking for outside activity. If nothing can be done, write in the handoff why and when to check again, and ask the project manager to assign work (the project manager tells the human and proposes one or two items to queue next) instead of waiting.

Before wrapping up or running out of context, append a section to `fleet/handoff.md` with its receiving role and task in the heading, using the [English handoff template](../fleet-setup/templates/en/handoff.md). Record progress, the next queued items (past any milestone, and which to do first if the first one is blocked), blockers, who takes over and when. State how to recognize success and failure, and what follows each. Include a directly executable resume command and its working directory. If the command reruns work or performs an external action, state the checks required first; do not make rerunning the default. If nothing is running, say so. At closeout, reconcile the entries already made and record any state changes; the project manager checks the project card.

Append only to `fleet/decisions.md`. Use the [English decision template](../fleet-setup/templates/en/decisions.md) for the date, decision maker, decision, reasoning, and evidence. For a decision that changes a practice or a rule, the reasoning covers five things: what gets better, what gets worse, how to soften what gets worse, what happens if nothing changes, and how to tell later whether it worked; a sentence or two is enough for a small change. When replacing a decision, add a new entry that references the old one. Keep the original entry as it was. Take dates and times in handoffs and decisions from the system clock (for example, run `date`, or `Get-Date` in PowerShell on Windows) right before writing them; do not estimate them from the conversation.

Reopen the records after writing. Verify that relative paths and command inputs exist within the project, and name the receiving role. Label judgments “Observed”, “Inferred”, or “Guessed”, using the project's language; say “Insufficient evidence” when evidence is missing. Return the added sections and remaining actions. If an existing decision cannot be confirmed or a resume command crosses an authorization boundary, preserve the current state, show the specific conflict and your recommendation, and check the approval table for the person or role authorized to decide. Ask them to resolve that conflict or explicitly approve the stated action and scope. Check the reply against the project rules, record it, and verify the command's inputs with read-only checks before resuming. If still unresolved, ask only for the next missing detail. Never request keys or passwords; direction, external commitments, spending, and deletion require human approval first.
